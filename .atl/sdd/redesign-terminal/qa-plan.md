# QA Plan — redesign-terminal

## 1. Contexto

El cambio `redesign-terminal` es **solo piel visual** sobre React + Tailwind (tokens, tipografía, Hero terminal, restyle de cards/forms, retiro del tema claro/oscuro). No hay lógica nueva: ni hooks de negocio, ni endpoints, ni estados de datos. Los datos de `src/data/*.ts` se consumen tal cual (restricción dura §6.1 de la spec).

**Runner**: el proyecto NO tiene runner de tests configurado (no existe `vitest.config*`, `jest.config*`, ni dependencia de `@playwright/test` / cypress en el directorio). Por decisión del plan:

- **NO se instalan dependencias nuevas** ni se añade un runner.
- El gate principal es **`npm run build`** (tsc + vite) — cubre "TypeScript sin errores", imports rojos/muertos y que la eliminación de ficheros (ThemeToggle, useTheme, ComingSoon, NotifyForm, Avatar si procede) no rompe el grafo.
- El resto de criterios de la spec se verifican con **greps/verificaciones estáticas** (`rg`, `ls`) sobre `portfolio/src/`, `portfolio/index.html` y `portfolio/tailwind.config.js`.
- Las aserciones de estado/BDD se expresan como "valor exacto esperado" (no solo smoke "existe"): conteos `== 0`, presencia de líneas concretas, ficheros ausentes.

Todo el plan es ejecutable en **un solo run** (una sesión de bash: 1 build + ~15 greps/ls), sin navegador, sin dev server.

**Directorio de trabajo de cada comando**: `/home/acuelop369/Escritorio/Proyectos/portfolio/portfolio` (código). Los greps de `index.html` y `tailwind.config.js` operan también ahí.

### Resumen de ejecución

Orden de run (una sesión, sin browser):

1. `QA-01` — `npm run build` (gate; aborta el run si no es exit 0).
2. `QA-02 … QA-20` — greps/ls secuenciales; cada uno imprime comando + valor obtenido + PASS/FAIL.
3. Cola final: `grep` de 2.ª pasada agregada (design §8 corte 3): `rg "rgba\(16, ?185|10b981|Geist|font-sans\|--|ThemeToggle|useTheme|ComingSoon|NotifyForm"` sobre `src/` e `index.html` → 0 hits (sanity antes del veredicto).

Resultado global: **PASS** solo si QA-01 exit 0 y todos los greps obligatorios (QA-02..QA-17) cumplen; QA-18..QA-20 son informativos (presencia de copy flexible / opcional), su fallo se reporta pero no bloquea el veredicto.

## 3. NOT cubierto (queda en sdd-verify / ojo humano)

El QA estático + build NO cubre los siguientes puntos de la spec; quedan para `sdd-verify` o revisión manual con `npm run dev` (375px / 768px / 1280px):

1. **Renderizado visual real en navegador** en los 3 breakpoints (AC §7.10 y §6.5): el QA-16 comprueba las clases de colapso (`min-w-0`, `flex-col`, `pre-wrap`) en el código, no que el Hero quede en una columna sin overflow horizontal real a 375px de viewport. Sdd-verify debe hacer el recorrido devtools.
2. **Contraste percibido** (`dim` #5f7a66 sobre #0a0f0d, ámbar, azul): se puede estimar aritméticamente, pero el QA no valida "legible" ni jerarquía visual; comparar contra el mockup `design-mockups/conceptos.html` con screenshots.
3. **Animación de tecleo en vivo** (framer-motion, 40-80ms por char, salto 300ms, timings `i * 0.35` del reveal): el QA-15 comprueba que la rama y la dependencia existen, no el timing ni el render final en pantalla (AC §7.9 reduce: texto final + cursor estático — requiere emulación `prefers-reduced-motion` en devtools).
4. **Cursor parpadeando** realmente con `blink 1.1s steps(1) infinite`: QA-09 valida el keyframe/CSS, no el render en vivo.
5. **h1 weight 700 computado** (AC §7.7): el QA valida que el bloque Google Fonts pide 700 y que el h1 lleva `font-bold`, pero **no** que el navegante no reciba síntesis de peso por un fallo en el CSS2 URL o blockeo de fonts.googleapis.com. Verificar en devtools (computed font-weight) o con screenshots.
6. **font-display swap en runtime**: `display=swap` está en el URL; su comportamiento con conexión lenta requiere Network throttling en devtools.
7. **`/cv.pdf` descargable en runtime** (AC §7.9): `ls` confirma que el fichero existe y el Hero lo enlaza (QA-13), pero no que el servidor sirva el MIME de PDF tras deploy (`npm run preview` o el deploy real).
8. **Recorridos manuales de flujos completos** (design §9 "Regresión"): drawer móvil, modal de proyecto (abrir/cerrar, callout info `bg-tertiary-container/40`), formulario de contacto con éxito y error reales, dots de carousel con interacción — el QA solo toca clases/hex, no interacciones.
9. **localStorage.theme en runtime** (Scenario "Tema único", spec §1): el QA comprueba la ausencia del script anti-FOUC y del `.dark`, pero "que la clave `theme` de localStorage no produzca efecto" requiere probar en navegador con la clave precargada en un perfil sucio.
10. **Screenshots comparativos contra el mockup** (`design-mockups/conceptos.html` CONCEPTO A): decisión visual humana (fiel al mockup vs. libre), no automatizable.
11. **`npm run preview` (SSR del HTML compilado)**: si `sdd-verify` quiere comprobar el HTML final del build (los greps QA-05/QA-07 corren sobre `index.html` fuente, no sobre el dist); opcional, añade 2 min al run.
